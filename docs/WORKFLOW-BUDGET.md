# 有界工程任务的执行预算

`--timeout` 不是“每一步各有这么多秒”。一次 CLI 处理过程中的服务请求共享期限，
workflow 的前置规划、嵌套读命令、叶操作和必要读回都消耗同一预算。
每次 RPC 只能使用剩余时间。预览和确认是两个独立调用，各自计时。
默认仍为30秒，普通范围仍为0.1到300秒；没有自动延长。

普通调用的单个服务请求仍最多等待120秒。只有下述明确启用的长预算profile，
才允许一次CLI调用最多1200秒、单个服务请求最多300秒。
每次RPC还受本次CLI剩余时间限制，总预算不是每个请求各自的预算。
请求已开始后触及服务上限，仍可能继续在Creo中运行，不能自动重试。

期限用于限制新的派发和服务等待，不是强杀 CAD 的定时器。
尚未开始的服务队列工作可以撤回；已经开始的原生工作不能据此承诺取消。
最终本地记录、输出序列化和进程启动另有开销，因此宿主进程的等待预算应留出余量。

## 明确启用图纸长预算

仅精确列入支持清单的现有命令可以使用大于300秒、最多1200秒的`--timeout`。
这会选择`drawing-complete-v1`，不增加新命令或扩大原有写入范围。
支持范围包括部分图纸读写、`model show`、`model save`、`model close`和`artifact export`。
它不涵盖所有`drawing`命令，也不扩大workflow的300秒上限。
完整清单以`reference.extensions.creo.drawing_execution_budget`为准；
对具体命令运行`reference --command '<命令路径>'`，核对
`command.extensions.creo.execution_budget`中的预算范围。

长预算必须在任何CAD调用前通过process-only capability检查，要求实际服务声明
`drawing_execution_budget: 1`。旧服务或缺少该capability的服务会拒绝，
不会降回普通profile继续调用CAD，也不会通过长timeout推断服务支持。
process-only health只证明连接及所声明的能力，不证明原请求结束或实例可恢复。

一个长预算调用共享所选总时间，覆盖前置准备、写入、首次必需独立验证和效果记账。
profile与总预算会冻结进预览绑定。确认必须沿用相同命令参数和相同`--timeout`；
不能拿300秒的预览令牌改成600秒确认。预览和确认仍是各自计时的独立调用。
公开计划及回执的`extensions.creo.execution_budget`记录profile、总秒数和单请求上限；
只读调用使用显式`--timeout`和reference中的合同；固定的`meta`不新增产品字段。

长预算不省略必要getter、首次独立读回、目标身份检查或原有保护条件。
1200秒是可选上限，不是必定完成的保证。预算不足时仍保留真实失败、unknown及已完成事实。
health成功不恢复旧pending调用，也不解除既有停止状态。
换Client、换实例或加大timeout也不恢复旧调用。

## 先观察再选择预算

workflow 预览的 `extensions.creo.execution_budget` 给出本次已观察到的准备耗时、
剩余时间、写步骤数及提示。准备阶段已占预算三分之一时会提醒；它不是后续耗时上界，
不能从几次调用的平均值保证所有模型、界面状态和磁盘条件都能完成。

公共计划／回执的 `extensions.creo.timing` 记录阶段和 RPC 计数。
阶段 seconds 为含子阶段时间，self_seconds 排除已计时子阶段，不能把含子阶段值相加。
RPC 时间包含排队、传输和服务工作，不等于原生 CPU 时间。
持久报告截于自己的最后一次回执提交之前；`meta.duration_ms` 另给整体命令处理时间。
失败记录、子回执和剩余步骤始终以操作记录为准。

第十二轮原 12 步任务曾在 CLI 280 秒／宿主 300 秒下约 289 秒返回 unknown。
第十三轮用等价的已保存准备件补测时，原版约 158 秒完成。前者仍是失败记录，
后者只说明当前条件下的一个观察；不能把环境时延变化当作优化收益。
最终候选对照、组件身份和统计分母见本轮证据摘要。

## 显式预算与拆分

根据当前任务的实际测量，给预览和确认相同的明确预算，例如：

```powershell
./creo-cli.exe workflow run --request task.json --timeout 280 --dry-run
./creo-cli.exe workflow run --request task.json --timeout 280 --confirm '<预览令牌>'
```

若一次预算容不下，拆成多个分别预览的任务：

1. 材料、标准和目标公差，随后独立读取确认。存在表归属时保持标准前序关系。
2. 再生成、独立读取、保存，并检查实际文件版本与 modified。
3. 只对当前组件已获资格的关联图纸执行编辑、保存及PDF输出；冻结的STEP交付仍须拒绝。

每段从实际已验证状态生成新计划，不能沿用变化前的确认令牌。
创建模型／图纸和新 ID 的准备仍使用明确叶命令，不因此开放动态 workflow。
32 步是数量上限，不能推导出时间承诺。

## 超时后的明确剩余任务

先用本地`operation show`查看父子记录。它不访问CAD。
如果原生读取未决，或请求可能已发送而开始、完成状态不明，先停止该实例的CAD派发。
此时只查看本地记录、process-only诊断及OS状态，不执行`operation query`或模型读取。
这些观察本身不证明getter已结束。换CLI、换Client或加大timeout也不是恢复。
只有独立核实原调用及实例状态后，才能读取实际模型、查询或登记。
保留completed、failed、unknown、skipped的区别；新任务只写明确剩余动作。
保存成功但丢回复、最终回执写入失败和进程被结束都不允许自动重放。
保存之后再改动仍可能 unsaved，导出成功也不能证明原生模型已保存。

`request_sent=false`只说明触发该异常的那次请求；父任务之前可能已有写入。
`failed_stage=verify`也不是原生派发journal，不能单凭它判断setter已完成。
例如本轮plate关闭的原始超时同时带有`failed_before_write`和`dispatch_state=unknown`。
维护者先结合准确产品源码、两次隔离HTTP对照和当前实例观察，判断它发生在关闭写请求的派发前。
之后独立读取确认plate仍在，才为这个剩余动作建立新计划，使用120秒预算。
原失败、原确认token和先前五次成功关闭都保留，没有重放。
这个有限案例不构成其他timeout的自动恢复规则。

期限耗尽的位置决定能保留哪些事实：

| 边界 | 可保留的事实 | 后续处理 |
|---|---|---|
| 子步骤派发前 | 该步骤零原生写入；父任务此前完成步骤仍保留 | 当前保存状态读不到时仍可 unknown，不能把它解释成已派发 |
| 写入后的验证期间 | 写入可能已完成，独立后置证据不足 | 保留产物、子回执与父 unknown，跳过后续步骤 |
| 子成功回执之后、父边界推进之前 | 子步骤保持 completed，原成功回执不变 | 父任务可能 unknown；不得把子成功改成失败或从头重放 |

每条失败记录应分别列出耗时与 RPC 数；少调用不等于墙钟更快。当前样本不证明墙钟加速。

## 含表格图纸的测量边界

分别记录前置准备、服务写入及其返回摘要、首次必需独立读回、后续效果记账。
服务返回内复用刚读到的同一表行，只减少服务返回阶段的重复遍历，不能替代首次独立验证。
写后独立观察成功后才建立的Plan缓存，也只能省去后续采样；首次读取失败时没有这项收益。

表格行列数、返回序列长度及同一segment的TableInfo可以在本次读取栈内复用。
每个单元格的文字、cell-note归属和原生部件引用仍要取得；可选null保持原值，不能补成空白。
新的命令、图纸、Plan或写入后的第一次读取重新观察，最终fresh依赖绑定和漂移检查仍执行。
独立BOM和气泡观察先核对实际图纸、唯一装配关联及实际装配身份，错对象不能成为效果证据。

真实含表读取必须使用来源冻结的保存副本、实际资格核验的实例和预先声明的有限次数。
一次基准的耗时不保证后续确认完成；只读基准本身若未决，同样停止该实例并保全现场。
既有停止实例的unknown和恢复限制不因独立副本测试而改变。
普通预算上限仍为300秒；长预算必须满足前述精确命令和服务capability条件。

正常`model close`也要单独测量。当前Plan的最终新鲜依赖读取，同时用于路径授权、
token绑定和未决操作检查；前置检查仍独立执行。关闭后先独立读取完整会话状态，
核对目标移除、其他模型及窗口保持。只有全部必要检查通过，同一Plan和Client才能
把这次完整观察用于随后效果记账。失败、不完整或未决读取不能建立成功cache。
这项复用不覆盖discard、query或resolve，也不证明首次独立读回必然在预算内完成。

### 视图验证通过后的再次读取

R37的S6正常参考视图确认耗尽300秒。原setter已返回，随后首次独立读取完成，
15项声明检查通过；之后效果记账又读取整张图，剩余38484ms耗尽并触发原生读取未决。
因此原回执同时保留execution completed、selected verification passed，以及
change/persistence unknown。这些阶段不矛盾，也不能改写成工程完成或已保存。
原B停止保持；查看本地记录或一段getter结束记录都不能证明原请求终态。

修正后的view add仍在独立读取后检查实际图纸、模型、页、唯一视图身份、Boolean及原资源。
只有全部必要检查通过，且同一Client、Plan与冻结请求等内容保持，才复用实际视图名称清单
用于效果记账。setter回复、旧Plan、错误对象、不完整或未决读取都不能建立这项缓存。
最终fresh依赖闭包同时用于路径授权和绑定，独立preflight仍保留；query/resolve重新读取。
这项修复减少已定位的重复读取，不承诺首次读取或含表格确认一定在300秒内完成。

### 普通注释的返回摘要

R37的C使用S7客户端及S5 JAR。六行普通注释确认约226.8秒返回unknown：
创建、Show和repaint已返回，服务摘要完成第一次六行读取；随后返回单条注释时，
又重复读取同一对象，在这次服务请求的120秒等待边界返回已开始、结果未明。
客户端首次独立验证尚未派发。原回执和停止状态保留，不能把helper返回改写成完整成功。

后续修正只在同一次服务摘要中按实际创建ID唯一选择原生注释行，保留真实图纸归属、
inventory membership及已取得的属性。缺行、重复ID、错误归属或必要证据不完整时拒绝，
不回退到再次读取或重新创建。可选空值及不完整包络保持原样。
客户端的首次独立验证仍读取当前状态；query和resolve不使用这份服务返回缓存。
源码测试不证明新构件已经满足原生预算，也不解除C、B或S3的停止状态。

### S8真实BOM失败与S9资格边界

R37的S8在真实BOM确认中，前置准备耗时188.144秒，随后服务写入及返回阶段
等待111.776秒后预算到期。首次客户端独立验证尚未派发，保存后的BOM数量也未验证。
原记录保留execution及change unknown。
persistence仍为unsaved，verification仍为incomplete。
实际getter记录及已观察到的表ID不能证明整个handler完成，也不能解除D的停止状态。
测量来源是保留现场的`D-S8-BOM-BUDGET-FORENSICS/REPORT.json`，
其源码基线为`7fc878ced438a5d9a879862cc62b13c936ff5cda`。

该失败说明300秒未容纳本次准备及服务返回，更长的客户端预算本身也不会改变
普通服务请求的120秒上限。S9因此引入明确选择的长预算合同，并保留全部必要读取。
S10在独立E副本中完成一次BOM确认，CLI耗时568.515秒。
第一次独立表格与装配读取在命令内完成，核心项号、模型、数量及实例对应通过；
三行NOTES文字读取失败、完整装配保护、布局和保存仍另列。
该结果不改变原S8失败，也不代表整份说明工程通过。

随后同一E上的气泡预览耗时579.187秒，只剩约21秒；没有派发气泡创建。
这次实际准备耗时说明600秒无法为确认中的写入和首次必需独立验证提供充分余量。
因此当前合同将明确选择的总预算上限调整为1200秒，原生单请求仍最多300秒。
旧600秒预览不能直接改用1200秒确认；必须保留旧计划，再建立相同新预算的预览与确认。
这是有限的公开预算调整，不是自动延长、恢复未决请求或完成保证。

仅BOM和气泡的同次preflight与domain plan共用成功的getter观察，
每条命令和每个Client都有独立观察边界。BOM模板仍实际读取并核对文件身份和摘要。
这段观察在最终fresh依赖闭包之前结束；确认时的漂移检查、原生派发、
首次写后独立验证以及query/resolve都不使用这份前态缓存。
失败、不完整结果或错误对象不能因复用成为成功的效果依据；pending及diagnostic仍优先阻断。
图纸的table、note和view库存必须实际返回列表，且每行ID可读取并且唯一。
缺失或有歧义时，计划与首次独立读回都明确返回incomplete，不用空列表代替。
这不把可选单元格文字读取失败或alignment错误改成完整属性，也不补默认值。
依赖读取遇到原生diagnostic时保留原错误、请求关联和停止指引，普通读取错误仍分别处理。
分别测量准备阶段和首次写后读取，不能用缓存命中次数承诺耗时。

r20b的稳定工程状态不变，既有B、C、D及S3停止记录不因这些调整改变。
